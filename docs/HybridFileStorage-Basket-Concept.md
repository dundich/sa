# Sa.Hybrid* — концепция «папка Basket как набор бэкендов»

Статус: **решения приняты** (см. [Решения](#решения-приняты)), план работ — следующий шаг.

## Целевая модель

Каждый тип storage (fs, pg, s3, mem) **регистрирует виртуальную папку Basket** и добавляет
к ней свои специфические параметры:

- **fs** — абсолютный путь (`BasePath`);
- **pg** — **ветка LIST-партиции** (`basket`) одной таблицы; схема/таблица — параметр
  уровня провайдера (одна таблица на БД), инстанс — строго **один на папку**;
- **s3** — бакет / эндпоинт / префикс;
- **mem** — параметры пула.

К одной папке можно повесить **комбинацию**: два fs с разными путями, два S3-бакета,
fs + pg + s3 одновременно. pg в папке — **не больше одного** (см. решение 7):
«две pg» = две папки = две ветки партиций одной таблицы.

Работа с папкой идёт **в порядке регистрации storages** (failover-цепочка); порядок
можно переопределить **явным списком типов** — глобально и/или на папку
(см. решение 8: «настройка не пуста → берём порядок из неё, по наличию типов»).

Варианты комбинаций должны быть описаны в readme всех `Sa.Hybrid*` пакетов.

## Что уже работает (one-shot)

- Ядро `Sa.HybridFileStorage`: `HybridFileStorageContainer` хранит storages в порядке
  добавления, `UploadAsync(basket, …)` фильтрует по имени папки и обходит их по порядку;
  `EnsureWritable` учитывает все хранилища папки.
- In-memory уже регистрируется многократно (тесты `FailoverTests` / `InterceptorTests`
  с двумя `shared_basket`).
- Семантика failover-цепочки уже покрыта тестами.

### Оговорки по порядку регистрации

Порядок в целом совпадает с порядком вызова `Add*`, но:

- хранилища, добавленные через `ConfigureStorage(...)`, всегда идут **после** всех
  DI-зарегистрированных, невзирая на порядок вызовов;
- in-memory, зарегистрированный внутри
  `AddSaHybridFileStorage(b => b.AddSaInMemoryFileStorage())`, встаёт в позицию вызова
  самого `AddSaHybridFileStorage`, а не своего места в цепочке;
- два канала добавления (DI-коллекция и `ConfigureStorage`) не перемешиваются.

## Где не достижимо one-shot

> Статус с учётом решений: строки про pg **пересмотрены (решение 7)** — БД
> организована через партиции (`LIST (tenant_id, basket)` + `RANGE created_at`),
> папка pg = ветка партиции, **одна pg-инстанция на папку**. Общий
> `Sa.Data.PostgreSql` не трогаем; «две pg» = две папки.

| Сценарий | Блокер | Масштаб правки |
|---|---|---|
| Два fs с разными абсолютными путями | guard `FileSystemStorageRegistration` бросает на втором вызове; единственный unnamed `IOptions<FileSystemStorageOptions>` (второй `Configure` слепился бы) | локально в `Sa.HybridFileStorage.FileSystem` — named options / фабрика / снятие guard'а |
| Два S3 (разные бакеты/эндпоинты) | тот же guard; `IS3BucketClient` — typed HttpClient с фиксированным именем и один options-инстанс в `Sa.Data.S3` | выходит за пределы Hybrid-пакета (`Sa.Data.S3`), нужны два клиента |
| Две pg-папки (одна таблица, ветки `LIST (basket)`) | guard «different options throws»; singleton-схема `PostgresFileStorageSchema`; один граф `AddSaPartitional` (делегаты копятся в один singleton-билд); один `IPartitionManager` | `Sa.HybridFileStorage.Postgres` |
| Две pg-инстанции в **одной** папке | ~~в скоупе~~ **вне скоупа** (решение 7: один pg на папку; одинаковый fileId различать не нужно) | — |
| Два pg с разными БД | **вне скоупа** (одна БД — `Sa.Data.PostgreSql` не трогаем) | — |
| Роутинг двух backend одного типа в одной папке (fs, s3) | fileId (`fs://share/…`) одинаков для обоих инстансов; оба вернут `CanProcess == true`, а `ExecuteStorageOperationAsync` возвращает `false` от первого не бросившего storage и не пробует следующий | поведенческое изменение ядра + тесты failover |
| Семантика upload | «первый успешный» (failover) — **решено: оставляем как есть** | не требуется |
| Options из конфигураций для всех провайдеров | `FromConfiguration` есть только у fs и s3; PG вообще вне options-pipeline (eager `new` + `Validate()` при регистрации — задокументировано как fail-fast); InMemory принимает только instance | перенос PG на options-pipeline меняет **момент** fail-fast (`ValidateOnStart` против `Validate` при регистрации) |
| Строгий порядок регистрации | см. оговорки выше — два канала добавления не перемешиваются | ядро — нужно зафиксировать и задокументировать правило |

### Итог

**One-shot достижимо**: ядро (реестр папок + порядок + семантика пробора), in-memory,
readme, `FromConfiguration` для InMemory.

**Не one-shot**: multi-instance fs (граница пакета), S3 (вылезает в `Sa.Data.S3`),
несколько pg-папок (попутно может зацепиться `Sa.Partitional.PostgreSql`).

## Решения (приняты)

1. **Семантика операций** — upload остаётся failover: пишется в первый успешный backend
   папки в порядке регистрации. **Download/Delete продолжают пробор после `false`/
   «не найдено», но только среди storage того же `StorageType`** — это меняет
   `ExecuteStorageOperationAsync`: сейчас `false` от первого не бросившего storage
   возвращает сразу, и второй backend папки никогда не опрашивается. Тип-ограничение:
   кандидаты и так фильтруются по схеме fileId, правило делает это явным — после `false`
   инстанса типа `T` дальше опрашиваются только инстансы типа `T` (два fs — пробуем
   оба; fs → другой тип — останавливаемся). Исключения по-прежнему уводят на следующий
   storage любого типа (failover). «Нигде не нашли» → `false` без исключения.
2. **PG: партиции, один инстанс на папку.** БД организована через партиции
   (`LIST (tenant_id, basket)` → `RANGE (created_at)`) — **папка pg = ветка
   `LIST`-партиции**, таблица/схема — параметр провайдера (одна таблица на БД).
   Две pg-инстанции в одной папке **не проектируются** — «две pg» = две папки
   (решение пересмотрено относительно «две таблицы в одной папке»). Общий
   `Sa.Data.PostgreSql` не трогаем; guard в pg-провайдере снимается только
   под несколько папок (несколько `AddSaPostgreSqlFileStorage` с одной таблицей).
   Retention — **один на таблицу** (`ExpireDays`/`ForwardDays` мержатся last-wins —
   свойство дизайна `Sa.Partitional.PostgreSql`, задокументировать). DDL fileId
   не меняется, различение в SQL не требуется (в папке один pg).
3. **Options** — на каждую папку свой configuration-секция **плюс** приём готовых
   `IOptions<T>` экземпляров. Значит: `FromConfiguration(section)` для всех провайдеров
   (сейчас нет у PG и InMemory), named options по имени папки, и перенос PG на
   options-pipeline (с переносом fail-fast: `ValidateOnStart` вместо `Validate()`
   при регистрации).
4. **Одинаковый fileId у двух backend одной папки** — различать пробором: «пока не
   нашли» (см. п. 1), storageType каждого инстанса не менять. Для pg неактуально
   (п. 2: в папке один pg) — актуально для fs/s3.
5. **Breaking changes допустимы** — guard'ы повторной регистрации, поведение
   download, сигнатуры регистрации могут меняться (пакеты 0.x).
6. **Readme — все**: главный `Sa.HybridFileStorage/Readme.md` + `FileSystem` +
   `Postgres` + `S3` (en и ru), с разделом «папка = N бэкендов» и примерами
   комбинаций (два fs, fs+pg+s3; для pg — «папка = ветка партиций, по одному
   pg на папку»).
7. **Порядок пробора** — после `false`/«не найдено» цепочка продолжается **только
   внутри того же `StorageType`** (см. п. 1); upload-first-wins и failover по
   исключениям — между типами сохраняются.
8. **Порядок типов в папке — настраиваемый.** По умолчанию: порядок регистрации.
   Настройка — список типов (`[fs, pg, s3]`), **глобально на контейнер + override
   на папку**; подача — **оба канала** (configuration-секция + программный вызов на
   builder'е ядра). Решающее правило: **если эффективная настройка не пуста — берём
   порядок из неё, по наличию типов**:
   - перечисленный тип **без** зарегистрированных storages — игнорируется молча
     (без ошибки);
   - зарегистрированный тип, **не** перечисленный в списке — **не участвует** в
     операциях папки (игнорируется полностью: не пишется и не опрашивается);
   - **внутри одного типа — всегда порядок регистрации** (два fs — в порядке
     `Add*`-вызовов);
   - приоритет: непустой override папки → непустой глобальный список → пусто/нет
     настройки = порядок регистрации, участвуют все типы;
   - фильтр применяется к **всей цепочке папки**: upload-кандидаты,
     download/delete-пробор, `EnsureWritable` (участников нет →
     `HybridFileStorageNoAvailableException`).
