# ADR-0003: In-memory провайдер внутри ядра `Sa.Outbox`

- Статус: Proposed
- Дата: 2026-11-03

## Контекст
Точка подключения `Sa.Outbox` описана тремя контрактами и одним вызовом `AddOutboxProvider`; в ядре
нет ни ADO.NET, ни какого-либо хранилища. Оба существующих провайдера требуют внешней
инфраструктуры: `Sa.Outbox.PostgreSql` — 6 852 строки и PostgreSQL, `Sa.Outbox.Redis` — 2 840 строк
и Redis Streams. Из этого следуют два пробела: пайплайн publish → rent → consume → acknowledge
нельзя прогнать без контейнера (28 из 46 файлов PG-тестов и 7 из 15 Redis-тестов поднимают
Testcontainers), а сама storage-логика (~40 строк в каждом провайдере) тонет в конфигурации, ключах
и guard-ах, поэтому пример встраивания провайдера фактически отсутствует.

## Решение
1. Добавить in-memory провайдера в сам проект `Sa.Outbox` (`src/Libraries/Outbox/Sa.Outbox/InMemory/`),
   неймспейс `Sa.Outbox.InMemory`, вход `AddSaOutboxUsingInMemory(...)`, дескриптор `"InMemory"`.
2. Реализовать только три контракта: `IOutboxBulkWriter`, `IOutboxDeliveryManager`,
   `IOutboxTenantDetector`. Capabilities: `TenantDetection | LockExtension | Postponement`;
   `PublishContext` не объявляется, non-null context отвергается.
3. Объявить назначение явно: reference-реализация и замена хранилища для dev/test. Без
   долговечности, без межпроцессной доставки, без health-проверки и прогрева, без poison-таблицы.
4. Код едет в существующем пакете `Sa.Outbox` (0.18.0 → 0.19.0); отдельный проект
   `Sa.Outbox.InMemory` не заводится.
5. Поправить формулировку «`Sa.Outbox` не знает, где лежат сообщения» в `PlugServices/Readme.md`:
   in-memory провайдер — единственное осознанное исключение, и он регистрируется через тот же
   `AddOutboxProvider`, а не в обход него.

## Последствия
Плюсы: пайплайн проверяется без Docker (первый такой набор в репозитории — `Sa.Outbox.Tests/InMemory`);
у автора нового провайдера появляется пример на ~300 строк вместо 6 000; приложения могут
использовать outbox в интеграционных тестах без инфраструктуры.

Минусы: ядро получает storage-реализацию, что размывает границу «ядро не знает о хранилище»;
пакет `Sa.Outbox` немного растёт; есть риск, что провайдер начнут применять в production —
смягчается явными ограничениями в README, комментарием в sample и этим ADR.

## Альтернативы
- Отдельный проект/пакет `Sa.Outbox.InMemory`: отклонено, потому что задача — показать встраивание
  провайдера рядом с контрактами и получить провайдер «из коробки» в уже подключённом пакете;
  вынос в отдельный проект механический (3 файла + csproj), если появится такая потребность.
- Положить провайдер в `src/Libraries/Sa` (shared-source base): отклонено как технически
  невозможное — `Sa.Outbox` линкует файлы из `Sa` через `<Compile Include>`, обратная ссылка дала бы
  цикл зависимостей.
- Только тестовый двойник в `src/Tests/Fixtures/Sa.Fixture`: отклонено, потому что он недоступен
  потребителям библиотеки и не может служить примером встраивания.
- Файловая персистентность для выживания рестарта: отклонено — это уже третье хранилище со своей
  атомарностью и восстановлением, а не Memory Outbox.
