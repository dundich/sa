# Secrets — Управление секретами

Класс `Secrets` даёт единый способ хранить и получать чувствительные данные — API-ключи, пароли к базам, прочие настройки — из разных источников. Он создан для безопасного доступа к секретам в приложении и позволяет подставлять значения в плейсхолдеры строк.

## Возможности

- **Цепочка хранилищ**: несколько хранилищ объединяются с приоритетом LIFO — побеждает то, что передано или добавлено последним. `AddStore` потокобезопасен (атомарная замена снимка). Встроенные хранилища:
    - Файл секретов: значения из основного файла (например, `secrets.txt`).
    - Секреты окружения: значения из файла под окружение (например, `secrets.Development.txt`) — разные настройки для разных сред.
    - Зашифрованные секреты: закоммиченные `secrets*.pub` файлы, зашифрованные AES-256-GCM (см. ниже).
    - `.env`-файлы: `KEY=VALUE`, `export KEY=VALUE`, кавычки, комментарии.
    - Переменные окружения: секреты, хранящиеся как переменные окружения.
    - Аргументы командной строки: секреты из CLI-аргументов через `Arguments`.
- **Подстановка плейсхолдеров**: значения подставляются в строки через `{{key}}`, например `"Database password: {{db_password}}"`.
- **Необязательные плейсхолдеры**: `{{?key}}` — если секрет не найден, вся строка становится `null` вместо исключения.
- **Защита от циклов**: вложенные плейсхолдеры раскрываются до глубины 3; циклические ссылки бросают `InvalidOperationException`.
- **Нормализация значений**: значения обрезаются по краям, обрамляющие кавычки (`'`, `"`, `` ` ``) снимаются.

## Порядок загрузки конфигурации

Цепочка по умолчанию (`Secrets.CreateDefault()`) разрешается с приоритетом LIFO — побеждает последнее хранилище:

| # | Источник | Роль |
|---|----------|------|
| 1 | `secrets.txt` | открытые значения по умолчанию |
| 2 | `secrets.{env}.txt` | открытые значения для окружения |
| 3 | `secrets.pub` | зашифрованные значения по умолчанию |
| 4 | `secrets.{env}.pub` | зашифрованные значения для окружения |
| 5 | `secrets.{client}.pub` | зашифрованные значения для клиента |
| 6 | `secrets.{client}.{env}.pub` | зашифрованные значения для клиента и окружения |
| 7 | `.env` | локальные переопределения; там же лежит ключ расшифровки |
| 8 | `.env.{env}` | локальные переопределения для окружения |
| 9 | Переменные окружения | перекрывают любой файл |
| 10 | Аргументы командной строки | наивысший приоритет |

`{env}` — это точное значение `Secrets.GetEnvironmentName()` (`DOTNET_ENVIRONMENT` → `ASPNETCORE_ENVIRONMENT` → `environment`, иначе `Production`). Для коротких имён вроде `dev` задайте `DOTNET_ENVIRONMENT=dev` — имена и открытых, и зашифрованных файлов следуют за ним.

Пути к файлам ищутся сначала относительно текущей рабочей директории, затем в `AppContext.BaseDirectory`.

### Пример

secrets.txt
```
# Postgres

sa_pg_user=user
sa_pg_password=password
sa_pg_host=localhost
sa_pg_port=5432
sa_pg_database=postgres
sa_pg_schema=public

# ElasticSearch
sa_es_connection=http://login:password@localhost:9202
```

appsettings.json
```
{
    "pg": {
      "connection": "User ID={{sa_pg_user}};Password={{sa_pg_password}};Host={{sa_pg_host}};Port={{sa_pg_port}};Database={{sa_pg_database}};Pooling=true;SearchPath={{sa_pg_schema}};Command Timeout=180;"
    },
    "es": {
      "connection": "{{sa_es_connection}}"
    }
}
```

## Зашифрованные секреты

Зашифрованные файлы предназначены для коммита. Значения зашифрованы, а имена ключей и комментарии остаются читаемыми, поэтому диффы и мержи работают как обычно.

### Формат файла

```
# saenc: v1
# saenc: kdf=pbkdf2-sha256
# saenc: iterations=600000
# saenc: salt=1sV7...==
# saenc: client=lsr
# saenc: env=Development
# Postgres
sa_pg_password=ENC1:QmFzZTY0...
```

- Каждое значение — `ENC1:<base64>`, где blob это `nonce(12) || tag(16) || ciphertext`.
- AES-256-GCM; ключ файла — `PBKDF2-SHA256(passphrase, salt, iterations, 32)` со случайной солью в 16 байт.
- Имя ключа аутентифицируется как associated data (`SAENC1|<keyName>`), поэтому значение нельзя «перенести» на другой ключ.
- Вместо парольной фразы можно использовать «сырой» 32-байтный ключ: с префиксом `base64:`; в заголовке тогда пишется `kdf=none`.
- Заголовочные `client` / `env` сверяются с именем файла. Несовпадение ломает старт.
- Зашифрованный файл должен содержать только значения `ENC1:`. Открытая строка `key=value` отвергается — не-секретам место в `secrets*.txt`.
- Комментарии и пустые строки сохраняются дословно; при дублях ключа остаётся последнее значение.

### Настройка

| Переменная | Смысл |
|------------|-------|
| `SA_SECRETS_DECRYPTION_CLIENT` | Клиент или список через запятую/точку с запятой. Побеждает последний. |
| `SA_SECRETS_DECRYPTION_KEY` | Глобальный ключ (парольная фраза или `base64:...`). |
| `SA_SECRETS_DECRYPTION_KEY_{CLIENT}` | Ключ для клиента; приоритетнее глобального. |
| `SA_SECRETS_DECRYPTION_KEY_FILE` | Файл с глобальным ключом. |
| `SA_SECRETS_DECRYPTION_KEY_FILE_{CLIENT}` | Файл с ключом для клиента. |

Те же настройки можно передать через `SecretOptions.Encryption` (`SecretEncryptionOptions`). Настоящая переменная окружения всегда побеждает `.env`.

### Создание и проверка файлов

В репозитории есть скрипт (тонкая обёртка над file-based приложением .NET 10):

```bash
# Зашифровать secrets.txt для клиента "lsr" и окружения "dev"
SA_SECRETS_DECRYPTION_KEY=... \
  ./build-sh/do-secrets.sh encrypt secrets.txt --client lsr --env dev -o secrets.lsr.dev.pub

# Вывести расшифрованное содержимое
./build-sh/do-secrets.sh decrypt secrets.lsr.dev.pub

# Проверить все зашифрованные файлы в текущей директории (удобно для CI, ненулевой код выхода при ошибке)
./build-sh/do-secrets.sh check
```

Ключ никогда не принимается значением командной строки — используйте переменную окружения, `--key-file` или интерактивный ввод. Локально работает и `SA_SECRETS_DECRYPTION_KEY=<key>` в `.env`.

`SecretsCipher` открывает ту же функциональность для собственных инструментов: `Encrypt`, `Decrypt`, `ReadHeader`, `SecretsFileHeader`.

### Поведение при ошибках

| Ситуация | Поведение |
|----------|-----------|
| Зашифрованный файл есть, ключа нет | `InvalidOperationException` с именем файла и ожидаемой переменной |
| Неверный ключ / повреждённый файл | `InvalidOperationException`, без отката к хранилищам с меньшим приоритетом |
| Заголовочные `client` / `env` не совпадают | `InvalidOperationException` |
| Ключ задан, файлов нет | ничего не происходит |
| Клиент задан, его файла нет | ничего не происходит |
| `SecretOptions.Encryption.Enabled = false` | зашифрованные файлы игнорируются |

### Замечания по безопасности

- PBKDF2-SHA256 по умолчанию использует 600 000 итераций (около 100–200 мс на файл при старте), минимум — 100 000.
- Nonce генерируется случайно для каждого значения; соль — для каждого файла.
- В git видны имена ключей и примерная длина значений. Если эти метаданные чувствительны, формат не подходит.
- Парольная фраза живёт в управляемой `string` и не может быть обнулена; предпочтительны «сырые» ключи `base64:` или файл с ключом.
- Ключ читается один раз при старте — для ротации нужен перезапуск.
- Формат несовместим с SOPS, git-crypt и age.

## Заключение

Класс `Secrets` упрощает работу с чувствительными данными: даёт гибкий и безопасный доступ к секретам из разных источников. С ним приложение остаётся настраиваемым и защищённым в любой среде.
